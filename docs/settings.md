## Управление: Action и WebUI

**Action** (кнопка ▶ у модуля в менеджере) переключает режим VPN ↔ напрямую. Демон
подтверждает переключение, и Action показывает понятный статус: где идёт раздача
(Wi-Fi/USB/…), режим, DNS раздачи и телефона, kill-switch.

**WebUI** (`webroot/index.html`, открывается из менеджера KernelSU) — основное место для
настроек. Все вызовы идут через `webctl.sh` с фиксированным набором команд. Значения
проверяет сам `service.sh --check` теми же правилами, что и при чтении конфига.
С v3.10 разделы разложены по вкладкам: **Главная** (режим и главные выключатели),
**Обход** (в том числе YouTube и QUIC), **Сеть** (DNS), **WARP** (с 3.19.0) и **Сервис** (до 3.19.0 —
«Инструменты»: проверки, журнал, «Отправить логи»). Что в них есть:

- **Переключить / Защита** — режим и kill-switch.
- **Диагностика сети** — подмена DNS, обрыв на ~16 КБ у зарубежных хостингов,
  белые списки (SNI), Telegram.
- **DNS** — DoH для раздачи напрямую, Meta «как из Европы», DNS раздачи при VPN
  (DNS VPN-клиента или «Как без VPN»).
- **Обход блокировок** — включение и режим zapret, YouTube-функции, сторож, своя стратегия
  для сайтов, журнал сторожа и подбора, стратегия текущей сети, свой список сайтов,
  встроенный список и автосписок, «Проверить сайт», «Скорость YouTube» (тем движком и той
  стратегией сети, что работают сейчас) и подбор стратегии (быстрый ~2 мин, полный ~7 мин).
- **Прочее / Дополнительно** — описание модуля, запасные DoH, bootstrap, интервалы проверок,
  настройки Meta, сброс всех настроек.
- **Журнал** — хвост лога демона и лог прошлого запуска.
- **WARP** — состояние туннеля, что идёт через WARP (Telegram, Google, домены, приложения
  целиком, «Для самого телефона», «Для раздачи»), конфиги: создать, импорт `.conf`/zip AmneziaVPN, вставить
  текст, «Основной», сохранить по одному и все в zip, удалить.

Кнопка «Применить» перечитывает настройки без перезагрузки. Раздача пересобирается, только
если поменялись DNS или kill-switch; zapret и QUIC применяются точечно, без обрыва соединений
клиентов.

## Настройки: `/data/adb/vpn_tether.conf`

Формат: `КЛЮЧ=значение`, всё после `#` — комментарий, кавычки вокруг значения допустимы.
Файл **не исполняется**. Читаются только ключи из `CONF_KEYS`, и каждое значение проверяется
(`_conf_set`). Неверное значение или неизвестный ключ пропускается, и это пишется в лог.
Если ключ убрать из файла, действует значение по умолчанию. Изменения применяются кнопкой
«Применить» в WebUI или после перезагрузки.

Флаги: `0` — выкл., `1` — вкл.

### Режим и защита

| Ключ | По умолчанию | Значения | Смысл |
|---|---|---|---|
| `KILL_SWITCH` | `1` | 0/1 | Правила VPN не встали или отвалились → трафик клиентов отбрасывается, а не уходит напрямую. |
| `KILL_SWITCH_STRICT` | `0` | 0/1 | 1 — выбран VPN, а VPN не поднят → клиенты без сети до появления VPN или ручного переключения. 0 — после 3 промахов раздача уходит напрямую. |
| `TETHER_STEALTH` | `1` | 0/1 | Скрыть раздачу: `net.tethering.noprovisioning`, TTL телефона 63, учёт пакетов раздачи с другим TTL. |
| `TETHER_TTL_STRICT` | `0` | 0/1 | Отбивать пакеты раздачи в мобильную сеть с «чужим» TTL (например, Windows: 127). Такое устройство без своей настройки TTL останется без интернета. |
| `NET_PROFILE_ADAPTIVE` | `0` | 0/1 | 0 — всегда профиль FAST, без пингов. 1 — пинг 1.1.1.1 через WAN раз в ~20 с; RTT выше порога или потеря 2 раза подряд → профиль STABLE (больше SYN-ретраев). В обоих BBR — только при поднятом VPN (TCP-туннелю он на потерях даёт в разы больше), напрямую cubic: 17.11 на YOTA с BBR у YouTube телефона было в 1,2–2,7 раза больше зависаний. |
| `STATUS_IN_DESCRIPTION` | `1` | 0/1 | Писать текущее состояние в описание модуля. |
| `QUIC_BLOCK_APPS` | пусто | имена пакетов через пробел | Закрыть QUIC (UDP 443, REJECT) этим приложениям телефона, чтобы они сразу шли по HTTPS. |
| `QUIC_BLOCK_YT` | `1` | 0/1 | Закрыть QUIC и установленным клиентам YouTube (YouTube, Music, Kids, ReVanced, ReVanced Extended, Morphe, Vanced, NewPipe, LibreTube) и Google Play — без добавления вручную. По HTTPS модуль может оборвать медленное видеосоединение и отбить молчащий сервер, по QUIC — нет (это при `ZAPRET_ENABLE=1`, `ZAPRET_PHONE=1` и без VPN; через VPN блокировка просто переводит YouTube на TCP в туннеле). |
| `QUIC_YT_FAKE` | `0` | 0/1 | Клиентам YouTube и Google Play вместо закрытия QUIC — подделка (nfqws: 6 поддельных QUIC Initial google.com, как в magisk-zapret2). На YOTA голый QUIC YouTube режется молча, с подделкой работает, перемотка быстрее. Действует, пока обход включён и nfqws работает (и есть `connbytes`); обход выключен или nfqws упал — закрытие. Через VPN/WARP QUIC YouTube не подделывается и не закрывается — идёт в туннеле. Ручной список `QUIC_BLOCK_APPS` главнее. AdGuard закрывает UDP 443 фильтруемым приложениям — модуль ставит в начало его цепочки RETURN для клиентов YouTube и подделок nfqws (сверяет каждые ~30 с): QUIC YouTube AdGuard не фильтрует, реклама через AdGuard может вернуться. |

### DNS

| Ключ | По умолчанию | Значения | Смысл |
|---|---|---|---|
| `DNSPROXY_ENABLE` | `1` | 0/1 | 0 — dnsproxy не используется вообще: DNS как в версиях до 1.1 (принудительно `DNS_DIRECT=plain`, `DNS_VPN=dnat`, `DNS_PHONE=0`). |
| `DNS_DIRECT` | `doh` | `doh` / `plain` | Режим «напрямую»: `doh` — `DNS_UPSTREAMS` через dnsproxy; `plain` — DNAT на 1.1.1.1. |
| `DNS_VPN` | `dnat` | `dnat` / `cache` / `doh` / `geo` | Режим VPN: `dnat` — DNS VPN-клиента (нужен, если клиент маршрутизирует по доменам/fakeip); `cache` — DNS VPN через dnsproxy с кэшем; `doh` — `DNS_VPN_UPSTREAMS` через туннель с кэшем (замер: ~200 мс вместо ~550 мс, из кэша ~5 мс); `geo` — как без VPN: `DNS_UPSTREAMS` (и запасные) через туннель — клиенты получают те же адреса в обоих режимах, и после выключения VPN сервисы с блокировкой по стране открываются сразу, без сброса кэша DNS. С `geo` маршрутизация VPN-клиента по доменам для раздачи не работает. |
| `DNS_PHONE` | `1` | 0/1 | DNS-запросы приложений телефона (:53) идут через dnsproxy, пока VPN не поднят. |
| `DNS_UPSTREAMS` | `https://dns.google/dns-query` | адреса через пробел | Основной DNS — для всех имён, кроме гео-списка: DoH `https://`, DoT `tls://`, DoQ `quic://`, обычный `ip:53`. С 17.11 по умолчанию обычный DoH с настоящими адресами (до этого — гео-DoH для всего: он подменял и не ИИ — `www.googleapis.com`, `api.github.com`, 4PDA). Google первым: на Android 8 у Cloudflare нет корня сертификата в системе. |
| `DNS_FALLBACKS` | `https://cloudflare-dns.com/dns-query https://dns.quad9.net/dns-query https://dns.adguard-dns.com/dns-query https://doh.libredns.gr/dns-query` | адреса через пробел | Запасные основного, только шифрованные. При сбое основным становится первый по порядку, который отвечает и которого нет среди основных (замолчал и он — следующий); за ними — гео-DoH из `DNS_GEO_UPSTREAMS` (тогда для всех имён: при ограничениях сети у них больше шансов, чем у оператора), и только потом DNS оператора. Мгновенными запасными dnsproxy (`-f`, их спрашивают все сразу на любом сбое основного) гео-DoH не бывают, даже если записаны здесь: чужим именам они отдают свои прокси (quic.best на `www.googleapis.com`, 18.11). Если гео-DoH ошибся на запросе, при `DNS_GEO_STRICT=1` запасные гео-имени адреса не дают. Пусто — без запасных. В WebUI основной и запасные — один список: первый — основной, ▲▼ меняют порядок, свои адреса — наравне с известными. |
| `DNS_GEO_UPSTREAMS` | `https://doh.fuckingspeedtest.com/dns-query https://dns.semqka.xyz/dns-query https://dns.commonnet.work/dns-query https://not-a-dns.quic.best/dns-query https://w.quic.best/dns-query https://sync.bezmezhau.com/dns-query https://dns.geodema.love/dns-query https://dns.dagami.ru/dns-query https://dns.zapret.moe/dns-query https://dns.keyoneday.ru/dns-query` | адреса через пробел | Гео-DoH (17.11): имена гео-списка (`dns/geo.txt` модуля и `DNS_GEO_DOMAINS`) dnsproxy спрашивает у одного из них — первого живого, остальные имена — у основного. Без VPN и при `DNS_VPN=geo`. Раз в минуту, только когда DNS спрашивают, модуль проверяет текущий (живой — любой ответ HTTP): замолчал — следующий живой по порядку; на запасном раз в 30 мин пробует вернуться к первому; молчат все — гео-имена идут в основной (настоящими адресами), перепроверка раз в 5 мин. В статусе — `dns_geo`. Пусто — гео-DoH выключен (гео-имена через основной). В WebUI — список с порядком, как у основного. |
| `DNS_GEO_DOMAINS` | пусто | домены через пробел | Свои имена для гео-DoH (с поддоменами) — к списку модуля. `dns/geo.txt` — 219 доменов из списка сервисов dns.zapret.moe (ИИ, Spotify, Notion, DeepL, JetBrains …; без тех, что их прокси не пропускает), собирается `tools/geo/build_geo.py`. |
| `DNS_GEO_STRICT` | `1` | 0/1 | Молчат все гео-DoH: 1 — сервисам гео-списка адрес не даётся (dnsproxy отправляет их имена на закрытый локальный порт, клиенту сразу «нет адреса»), пока гео-DoH не оживёт; 0 — настоящие адреса через основной DNS. Настоящий адрес этим сервисам почти бесполезен (закрыты для России по адресу), а приложения его запоминают и после возврата гео-DoH ещё минуты не работают; отрицательный ответ не запоминают. |
| `DNS_GEO_MODE` | `split` | split/off/all | Какие DNS спрашивать. `split` — основной список для всех имён, гео-DoH — для имён гео-списка; `off` — только основной список, гео-DoH не спрашиваются (сервисы гео-списка получат настоящие адреса); `all` — гео-DoH для всех имён: первый из `DNS_GEO_UPSTREAMS` — основной, остальные — запасные (часть из них отдаёт свои прокси и для Google). Сами списки в конфиге не меняются. |
| `DNS_VPN_UPSTREAMS` | `https://dns.google/dns-query https://cloudflare-dns.com/dns-query` | адреса через пробел | Апстримы для `DNS_VPN=doh`, идут через туннель. |
| `DNS_BOOTSTRAP` | `77.88.8.8:53 1.1.1.1:53 8.8.8.8:53` | `IP:порт` через пробел | Чем резолвить имена самих DoH-серверов. Подмена здесь не опасна: сертификат апстрима всё равно проверяется. |
| `DNS_HEALTH_INTERVAL` | `5` | 2–600 с | Как часто проверять DoH. Проверки идут только при реальном использовании DNS. |
| `DNS_HEALTH_RECOVER` | `30` | 2–600 с | Как часто в откате проверять, ожил ли DoH. |
| `DNS_VIA_ZAPRET` | `0` | 0/1 | Соединения dnsproxy с DoH-серверами — через обход (zapret). Нужен, если оператор режет DoH по имени (09.11 на YOTA — dns.zapret.moe, 18.11 — и cloudflare-dns.com). Имена DoH из `DNS_UPSTREAMS`, `DNS_FALLBACKS`, `DNS_GEO_UPSTREAMS`, `DNS_META_UPSTREAMS` (и `.ru`) получают свой профиль nfqws с постоянным приёмом, не стратегией сети (09.11 одна из 31 стратегий подбора ломала весь DoH). У nfqws2 — 2 нулевые подделки с плохим ack и разрез посередине имени (18.11: прежний md5sig перестал открывать cloudflare-dns.com и dns.zapret.moe, этот — 6/6), у nfqws1 — md5sig. Серверы, которые ломает любая подделка (LibreDNS, dagami), идут без приёмов. Смена списков DNS перезапускает обход; при запуске демона, пока обход не поднят, недоступный основной DoH перепроверяется через минуту, в любом режиме обхода и при обходе только для раздачи. DoH (`https://`, порт из адреса, иначе 443) и DoT (`tls://`, 853); серверы, заданные адресом, и запасной bootstrap DoH — отдельным профилем по адресу. DoQ (`quic://`) через обход не идёт. Запасные идут через обход тоже, поэтому если стратегия сломает DoH, DNS временно уходит к оператору (интернет есть, гео-блок не обходится), пока DoH не оживёт. |
| `DNS_META_EU` | `1` | 0/1 | Домены Meta (Instagram, Facebook, Threads, Messenger, WhatsApp) резолвит отдельный dnsproxy (127.0.0.1:5355) с ECS → приходят адреса европейских узлов. Только там, где DNS и так идёт через DoH без VPN. |
| `DNS_META_ECS` | `185.15.56.0` | IPv4 | Адрес «откуда спрашиваем» для EDNS Client Subnet (берётся /24, по умолчанию Амстердам). |
| `DNS_META_UPSTREAMS` | `https://dns.google/dns-query` | адреса через пробел | DoH для Meta. Сервер должен учитывать ECS: Google учитывает, Cloudflare — нет. |

### Обход DPI (zapret)

| Ключ | По умолчанию | Значения | Смысл |
|---|---|---|---|
| `ZAPRET_ENABLE` | `1` | 0/1 | Обход DPI для трафика мимо VPN. |
| `ZAPRET_ENGINE` | `nfqws2` | `nfqws2` / `nfqws1` | Движок обхода. `nfqws2` (zapret2, Lua) — стратегии из nfqws2-android (`ZAPRET2_STRATEGY`), многие сами меняют приём для сайта после неудач. Подбор (все стратегии nfqws2), своя стратегия для каждой сети (`ZAPRET_PER_NET`) и сторож работают и у `nfqws2` — свои файлы `vpn_tether_zapret2_nets` и `vpn_tether_zapret2_hist`; своя стратегия YouTube и Discord — только у `nfqws1` (у `nfqws2` они часть стратегии). Своя стратегия сайтов (`ZAPRET_ALT`) — у обоих: у `nfqws2` сайтам подбирается другая стратегия nfqws2 (запись `z2:<имя>`), профиль — её TLS-приёмы со списком этих сайтов. Нет бинарника или Lua или nfqws2 не запустился — модуль работает на `nfqws1`. Ядро без `connbytes` — тоже `nfqws2`, в упрощённом режиме: в очередь весь исходящий TCP, кроме порта 80 и пустых ACK (при закачке это почти все исходящие пакеты; issue #26), приёмы — на первых 20 перехваченных пакетах (`--out-range=-n20`; пустые ACK в счёт не идут, так что это примерно `connbytes 1:40`), UDP (звонки, QUIC) — мимо обхода, QUIC раздачи закрыт (замер 17.11: на пакет nfqws2 не дороже nfqws1, на Redmi 4X 120–160 мкс против 200–240). До 17.11 такие ядра работали на `nfqws1`: подобранные им стратегии сетей к `nfqws2` не переходят — до нового подбора общая стратегия. Часть приёмов hardcorp74 держится на метках времени TCP, а Windows их не ставит: для соединений без метки модуль меняет приём сам (`zapret2/lua/vpn-tether.lua`), включить метки на компьютере — запасной шаг (см. [вопросы в README](../README.md#вопросы-и-ответы)). |
| `ZAPRET2_STRATEGY` | `vt_soft_crck` | имя файла `zapret2/strategies/<имя>.conf` | Стратегия `nfqws2`: 35 наборов из nfqws2-android (авторы — `strategies/meta.tsv`) и своя по умолчанию `vt_soft_crck` (Kubarev): основа universal_v12 с 2 подделками вместо 6 и своей нарезкой, а видеосерверам (googlevideo.com) — две нулевые подделки и разрез посередине имени из hardcorp74; с 17.11 на пробу тот же профиль — загрузкам Play (gvt1.com) и картинкам (googleusercontent.com), раньше шедшим общим профилем по адресу Google. На SYN клиента — две поддельные копии SYN-ACK (synack): на YOTA TLS открывается вдвое быстрее (0,29 с против 0,55, стенд 16.11), волн не было; стоят последним профилем (`NFQWS_ARGS_SYN` — наше расширение формата стратегий), стойкам малого окна не даются. На YOTA (15.11) оборудование оператора режет видеосоединение, если его проходят 3 подделки и больше, а у anti_throttle их 6: кэш YOTA и часть стоек не открывались вовсе. Подделка TLS-части (сайты, API YouTube) — ClientHello www.google.com без подмены имени: .рф-имена (15–16.11) YouTube на деле не помогли. Из файла берутся только приёмы (основа, TCP, QUIC, UDP, свои профили стратегии); порты, режимы, списки, исключения и DoH — модуля. Подделкам, которые держатся на метке времени TCP, модуль сам добавляет `fool_nots` для Windows-клиентов. У стратегий с `ip_autottl` в TCP (anti_throttle, universal_v12/v13) видеосерверы вне сетей Google — кэши оператора — идут своим профилем: те же приёмы, но подделка не дальше 5 хопов. На YOTA ТСПУ стоит между 5-м и 6-м хопом: кэш с подделкой, дошедшей до него, не открывается, а API YouTube без неё — тоже, поэтому общий потолок нельзя. Нет такого файла — vt_soft_crck. |

Пусто — как в стратегии: у `vt_soft_crck` в самом файле `защитник.рф` (18.11), у остальных `www.google.com`. Подделка Google в общем профиле есть у 11 стратегий из 37, у остальных имя ставить некуда. ### WARP (с 3.19.0)

Туннель WARP (AmneziaWG, `amneziawg-go` + `awg`) работает только в режиме «напрямую» и только
пока VPN на телефоне не поднят. Проверка — `https://1.1.1.1/cdn-cgi/trace` через туннель;
не отвечает 3 раза подряд — следующий конфиг (этот — 10 мин мимо), все мимо — повтор через 5 мин. Через туннель
идут только выбранные группы, остальное — напрямую (с обходом).

У конфигов Cloudflare (Endpoint `engage.cloudflareclient.com`, `162.159.x` или `188.114.x`)
адрес подбирается (с 3.19.1): сети режут WARP по-разному — одни подсети, другие порты.
Сначала — адрес, который уже сработал в этой сети, потом адрес из конфига, потом список
`warp/endpoints.txt`. Нет хендшейка за 4 с — следующий адрес; не ответил ни один — следующий
конфиг; после двух таких конфигов подряд остальные пробуют только первые два адреса (WARP в
сети закрыт целиком — не гонять пул по каждому), до конца круга. Адрес, через который прошёл
трафик, запоминается для сети в `/data/adb/vpn_tether_warp/.endpoints`. Сеть определяется
только при включённом zapret со «своей стратегией для каждой сети» (`ZAPRET_PER_NET=1`),
иначе запись одна на все сети. Свой сервер AmneziaWG/WireGuard не трогается.

Площадка Cloudflare, через которую выходит WARP (`colo=` в trace), пишется в лог, в статус
(`warp_colo`) и в WebUI («Выход: Хельсинки, Финляндия (HEL)»). С российского адреса на
российских площадках (DME — Москва, LED — Санкт-Петербург, KJA — Красноярск) часть адресов
режется, в том числе Telegram, поэтому адрес, выводящий туда, модуль пропускает и берёт
следующий. Если другой площадки ни на одном адресе нет — работает через российскую, с
предупреждением в логе и жёлтой точкой в WebUI.

### Запасной выход Opera

Прокси Opera для отдельных сайтов, которым нужен иностранный адрес: `opera-proxy` (Alexey71, MIT) и
`hev-socks5-tproxy`. Работает для телефона и раздачи в режиме «напрямую», пока VPN не поднят. Только TCP и IPv4.
Регистрация в API идёт через бесплатные прокси из публичного списка: напрямую из России Opera отдаёт закрытые
адреса. Трафик сайтов через эти прокси не идёт, но его видит Opera.

| Ключ | По умолчанию | Значения | Что делает |
|---|---|---|---|

| `OPERA_COUNTRY` | `EU` | `EU` / `AS` / `AM` | Регион серверов Opera. Если запуск не удался дважды подряд (API выдаёт только закрытые адреса), третья попытка идёт через последний рабочий сервер региона (`/data/adb/vpn_tether_op_ep`), четвёртая и пятая — через другие регионы. На запасном регионе Opera остаётся до сбоя или смены сети. |
| `OPERA_TELEGRAM` | `0` | 0/1 | Сети Telegram; при `OPERA_PHONE=1` и клиенты Telegram целиком. Звонки не идут. |
| `OPERA_GOOGLE` | `0` | 0/1 | Сети Google без Google Cloud. |
| `OPERA_APPS` | пусто | пакеты через пробел | Приложения телефона целиком, только TCP. |
| `OPERA_PHONE` | `1` | 0/1 | Группы и сайты — для приложений телефона. |
| `OPERA_TETHER` | `1` | 0/1 | Группы и сайты — для раздачи. |
| `OPERA_DOMAINS` | `!4pda.to app.4pda.to` | домены через пробел | Точные имена, поддомены не добавляются. Адреса общих CDN пропускаются; `!домен` идёт и через них, тогда в Opera попадут и другие сайты на этом адресе. |

Пример для закрытых разделов 4PDA: `OPERA_DOMAINS=!4pda.to app.4pda.to`.

QUIC к этим адресам получает отказ, браузер переходит на TCP. IPv6 групп и приложений отбивается, IPv6 сайтов из
списка не трогается. Не включайте одно и то же в WARP и здесь: на телефоне приоритет у WARP, а на раздаче маршрут зависит от порядка цепочек.

Пример:

```ini
# раздача напрямую — DNS через DoH, телефон тоже
DNSPROXY_ENABLE=1
DNS_PHONE=1
# режим VPN без VPN-клиента — раздача на паузе
KILL_SWITCH_STRICT=1
# закрыть QUIC приложению
QUIC_BLOCK_APPS=com.example.app
```

## Как устроен обход DPI

Обход работает только **мимо VPN**: в туннель (`tun*`) и в соединения самих VPN-клиентов
модуль не вмешивается. Первые пакеты HTTPS-соединений из `mangle POSTROUTING` (цепочка
`VPN_ZAPRET`) уходят в nfqws, а первые ответы (`VPN_ZAPRET_IN`) — тоже в nfqws, чтобы тот
замечал обрывы и пополнял автосписок. nfqws работает с отдельной группой (GID 3998), и его
собственные пакеты узнаются по владельцу сокета. Метка пакета не подходит: на мобильном
интернете Qualcomm-цепочка `qcom_qos_reset` её стирает.

**Списки сайтов.** `zapret/list-default.txt` (~200 доменов: YouTube, Discord, X, СМИ,
сайты VPN, мессенджеры и т. д.), свой список из WebUI (`/data/adb/vpn_tether_zapret.txt`)
и автосписок, который nfqws пополняет сам (`/data/adb/vpn_tether_zapret_auto.txt`).
Для доменов `zapret/list-youtube.txt` может действовать отдельный профиль nfqws (`--new`).
Домены из `zapret/list-exclude.txt` (банки, Госуслуги) не обрабатываются никогда и не
попадают в автосписок. Зоны `.ru`, `.su` и `.рф` (`zapret/list-rutld.txt`) обход тоже не
трогает и в автосписок не берёт — кроме сайтов, явно перечисленных во встроенном или своём
списке (заблокированные издания): для них отдельный профиль с той же стратегией (с v3.8).

**Стратегии сетей.** Сеть определяет `zapret/netid.sh`: Wi-Fi — `wifi:<SSID>`, мобильная —
`mobile:<MCC MNC>` (сеть SIM с мобильными данными). Для каждой сети в
`/data/adb/vpn_tether_zapret_nets` запоминается своя стратегия, отдельно общая и для YouTube.
При смене сети nfqws перезапускается с её стратегией. Если для сети записи нет, берётся
стратегия сети с тем же названием (оператор бывает виден под разными MCC MNC), а если нет и
её — общая `ZAPRET_STRATEGY`. Встроенные стратегии проверялись сканером в 10 сетях:
`fakeddisorder` дала полный или почти полный результат везде, поэтому она стоит по умолчанию.

**Подбор (`zapret/scan.sh quick|full`).** Сканер проверяет стратегии запросами только самого
себя (`curl --interface <WAN>` от root, через отдельную очередь NFQUEUE 203). Трафик телефона
и раздачи не затрагивается. Адреса сайтов узнаются через DoH. Сначала сканер выясняет, что
заблокировано без обхода. Контрольные сайты без блокировок нужны, чтобы отличить блокировку
от отсутствия связи. Каждый сайт проверяется и обычным, и большим постквантовым ClientHello
(2 TCP-сегмента, как у Chrome/AdGuard): засчитывается, только если открылся обоими.
- **Быстрый** (~2 мин) — 22 проверенных шаблона: разрезы, подделки с md5sig/badseq/badsum/datanoack,
  `hostfakesplit` с приманкой google.com и российским SNI, seqovl, `--dup`.
  Сторож идёт по этому же списку, но останавливается на первой стратегии, открывшей всё без поломок.
- **Полный** (~7 мин) — 80 вариантов по этапам: разрез без подделок → виды подделок →
  подделка + разрез, приманки с российским SNI, разрез с наложением → варианты поддельного
  ClientHello и повторы для трёх лучших → новые приёмы (`--dup`, `--orig-autottl`)
  для двух лучших.

Затем лучшие три (плюс до двух лучших для YouTube) перепроверяются по два раза. Побеждает
стратегия, которая ничего не ломает и открывает больше заблокированного по худшему прогону, а
при равенстве — более быстрая. Для YouTube своя стратегия запоминается, только если она
открывает больше YouTube, чем общая.

**Сторож (`scan.sh check`, `ZAPRET_WATCHDOG`).** Раз в `ZAPRET_WATCHDOG_MIN` (15) минут, а
также сразу, если видеосоединения начали застревать на ClientHello, сторож проверяет стратегию
текущей сети. Если она сломалась, через минуту следует перепроверка. Когда не открылось вообще
ничего, включая контрольные сайты, это считается проблемой связи, а не ТСПУ, и стратегия не
меняется. Иначе сторож пробует прежние рабочие стратегии сети (`/data/adb/vpn_tether_zapret_hist`),
затем быстрый подбор. Работает только при своей стратегии для сети и без поднятого VPN.
События пишутся в `/data/adb/vpn_tether_zapret_events`.

**Своя стратегия для отдельных сайтов (`scan.sh sites`, `ZAPRET_ALT`).** Автосписок nfqws
замечает сбои только у сайтов, которых в списке ещё нет. Поэтому раз в `ZAPRET_ALT_MIN`
(1440) минут демон проверяет сайты из списков — ночью, с 01 до 06: днём сотни запросов к закрытым
именам запускали волну Google (на Wi-Fi адрес, на котором она держится, не сменить) (до 400, мимо VPN, без YouTube и исключений).
Сайтам, которые основная стратегия не открывает, подбирается другая (у `nfqws2` — одна из его
стратегий: сначала уже закреплённые и прежние стратегии сети и сетей с тем же названием, всего до 8 кандидатов; сайту достаются только её приёмы TLS, ими же она и проверяется): до 3 стратегий на сеть,
nfqws получает для них профили перед основным. Если сайт не открылся ничем, он сутки не
проверяется. Если адресов узнали меньше 60 % или «закрыто» больше 90 %, результат не
сохраняется и проверка повторяется через ~15 мин. Хранится в `/data/adb/vpn_tether_zapret_alt`.
Проверка, сторож и подбор после каждого прогона, где что-то не открылось, проверяют Google напрямую:
HTTPS молчит, а HTTP отвечает — волна ТСПУ, и они останавливаются, ничего не запомнив (дальше
каждый кандидат — снова закрытые имена, а итог в волну — мусор). Плановая проверка сайтов после волны
час не запускается (из WebUI — запускается).

**Повтор застрявших видеосоединений (`YT_DEAD_FAILFAST`, `YT_RETRY_MAX`).** Часть видеосерверов
Google принимает ClientHello, но не присылает ни байта, и плеер ждёт каждый ~27–30 с. Демон
помечает соединения с `googlevideo.com` и со стойками `gvt1.com` (имя `rr…---sn-…`: загрузки Play — те же
видеостойки; с 18.11, до этого молчащая стойка Play попадала в мёртвые фронты и 15 мин получала отказ; сигнала
сторожу от них нет, фронт `redirector.gvt1.com` — как прочие фронты Google) битом connmark и ищет их в conntrack (только мимо VPN,
пока включён zapret, только IPv4). Сервер не отключается: обход проходит не с каждой попытки, а
прежний отбой (RST адресу на 30 мин, с перепроверкой, проверкой молчащих, QUIC и Play Маркетом)
отправлял плеер искать другой сервер и в фоне оставлял его на закрытом — убран 15.11. Если ClientHello к `googlevideo.com` 1 с без ответа (`YT_RETRY_AFTER`, при большом RTT —
6×RTT) или сервер принял его и молчит 3 с, демон рвёт только это соединение (`ss -K`), и приложение
сразу открывает новое. Видеосоединения при этом просматриваются дважды за круг демона (раз в ~1,3 с),
иначе застрявшее замечалось бы только через 2–3 с.
Внутри старого соединения повтор не помогает: ядро шлёт тот же ClientHello в поток, который DPI
уже закрыл. Замер 14.11 на YOTA с hardcorp74: с первой попытки 28 из 40, за две — 35 из 40; худший
сервер за 1–5 попыток — 6, 9, 10, 11 и 12 из 12. Не открылся `YT_RETRY_MAX` раз подряд за минуту, а
видео нигде не идёт — это уже похоже на сломанную стратегию, и сторож её проверяет. Соединения
раздачи идут через телефон транзитом, и `ss` их не рвёт. Если ClientHello клиента не подтверждён,
на его повтор он получает RST (правило на одно соединение, 20 с) и сразу открывает новое.
Видеосерверы в WARP (`YT_DEAD_WARP`) и обрыв медленных (`YT_SLOW_RETRY`) убраны 15.11: с хорошей
стратегией и разрывом молчащих без них лучше, а отлаживать проще. Эти ключи в старом конфиге
демон молча пропускает.
Ещё один вид: соединение с видео живое, но запрос, отправленный по нему, остался без ответа —
шортс молчит, а если перелистнуть и вернуться, открывается. Если после последних данных сервера
клиент отправил запрос (больше 80 байт полезного), а сервер 2 с не прислал ни пакета, даже
подтверждения (`YT_REQ_AFTER`, у раздачи на 1 с меньше; не меньше 8×RTT соединений телефона),
соединение телефона рвётся, и плеер сразу открывает новое. Простаивающее в пуле
соединение (последним говорил сервер) так не трогается. 15.11 на YOTA таких было 16 за 7 минут
шортсов, а повторов ClientHello — ни одного. Клиенту раздачи (его соединение `ss` не рвёт) —
RST на повтор этого запроса: от сервера не пришло даже подтверждения, и клиент его повторит.
Соединения через WARP модуль только записывает в журнал.

Чаще всего такой запрос — первый после простоя. На YOTA (16.11) прямое соединение с видеосервером
Google после 10–20 с тишины на следующий запрос не отвечает (после 5 с простоя — 2 из 21, 10 с — 4,
15 с — 10, 20 с — 17), чаще на стойках малого окна. ТСПУ забывает поток: на стенде (7 стоек малого
окна, паузы 15 и 20 с) с TCP keepalive раз в 3 с после простоя умерло 7 из 50 соединений против 32 из 42
без него, а малое окно на запросе после паузы не помогло (33 из 38). Поэтому прямое видеосоединение к серверу Google, по которому `YT_IDLE_KILL` с (10, в
`service.sh`, 0 — выключено) не прошло ни пакета, модуль рвёт заранее (телефону — `ss -K`, раздаче — RST
на её следующий пакет), и плеер берёт новое. Простой — по таймеру conntrack. Шортсы A/B (16.11, 4 фазы
по 24 × 20 с): запросов без ответа к серверам Google 3 против 26 без обрыва, старт тот же (медиана
0,6 с). Кэш оператора и WARP не трогаются.

Обрыв, однако, ломал плеер: звук начинался заново, а картинка ждала, пока он догонит (16.11 — за 4 с
до этого оборвано простоявшее соединение к серверу ролика). Поэтому соединениям телефона модуль поток
держит, а не рвёт: если по прямому видеосоединению (к Google или кэшу оператора) `YT_POKE` с (3) ничего не шло, а данные от
сервера были не раньше `YT_POKE_MAX` с (120) назад, `bin/vtpoke` шлёт в него пустой ACK с чужим номером
— сервер отвечает своим ACK (RFC 5961), и ТСПУ поток не забывает. Стенд (7 стоек малого окна): после
15 с простоя умерло 2 из 31 против 15 из 17, после 60 с — 6 из 24 против 23 из 23. Дольше двух минут без
данных соединение не трогается (пул брошен; если его всё же возьмут — подстрахует «запрос без ответа»).
Раздаче (17.11) — тот же пакет с адресом WAN и портом после NAT; он идёт мимо conntrack телефона (правило `CT --notrack` в `raw` только для 40-байтного голого ACK модуля), и ответ сервера проходит обратный NAT до клиента. Стенд (клиент в netns за NAT, 6 стоек): после 15 с простоя умерло 0 из 36 запросов против 15, после 60 с — 0 против 20. Обрыва простоя раздаче нет. Нет `vtpoke`
или он не смог отправить — и телефону обрыв, как раньше. Счётчик — `yt_pokes` в статусе.

Когда молчит вся связь (метро, слабый сигнал, у Wi-Fi пропал интернет), зависшие соединения не рвутся
совсем: «запрос без ответа», «ClientHello без ответа», простой и мёртвые фронты тогда говорят о канале, а
не о сервере, а обрыв всего подряд оставлял плеер без соединений (17.11, метро). Признак — за проход на
интерфейс пришло меньше 2 КБ и нет ответа на пинг 77.88.8.8 за 1 с; трафик пошёл — снова как обычно.

**Мёртвые фронты (с `YT_DEAD_FAILFAST`).** Бывает, что мёртв не видеосервер, а фронт Google: 15.11 на YOTA
у `youtubei.googleapis.com` из 8 адресов в ответе DNS не отвечал 172.217.114.4 — рукопожатие проходит, а
дальше от сервера ни байта, даже на обычный HTTP; через WARP он жив, то есть это блок адреса на пути, и ни
стратегии, ни малое окно тут не помогают. AdGuard держал к нему соединения до 8 минут. Если у телефона
соединение к сети Google без пометки `googlevideo.com` (фронты, API) дважды за `YT_RETRY_WIN` за 1 с (6×RTT)
не получило от сервера после рукопожатия ни байта данных (ClientHello не подтверждён или подтверждён и
тишина; считаются и уже закрывающиеся соединения), новым соединениям к этому адресу 15 минут отвечается RST
на SYN, висящие рвутся — приложение сразу берёт другой адрес. Соединения, где сервер прислал хоть что-то
(выгрузки, долгие запросы), не учитываются; через VPN и WARP отказа нет — мёртв адрес на прямом пути. Список свой у каждой сети и недолгий: адрес,
мёртвый здесь, в другой сети или позже может быть жив; через 15 минут он пускается снова и, если всё ещё
мёртв, вернётся за два зависания. Если за 2 минуты замолчали 3 и больше адресов сети — это волна ТСПУ, а не мёртвый
адрес (16.11: за 5 минут молчали все 8 адресов API): отказы этой сети снимаются и 10 минут новые не
ставятся, иначе после волны приложение ещё долго не пускали бы к ожившим адресам. Не больше 16 адресов на сеть, первые 30 секунд после включения не
учитываются, DoH Google (8.8.8.8, 8.8.4.4) не трогается. С отказом 15.11: за 9 минут шортсов одна попытка к
мёртвому фронту и ни одного зависания API (без него 4 соединения висели до 8 минут). В статусе — «отказ
мёртвым серверам: N».

**Малое окно для молчащих серверов (`YT_WSSIZE_RAMP`, только nfqws2).** С конца октября 2026 ТСПУ
режет TLS с части адресов Google независимо от имени: узнаёт шифрование по началу ответа сервера
(`16 03 03`), но читает ответ лишь в пределах окна приёма, объявленного клиентом (вики zapret,
«TLS по адресу»). Если видеосервер (соединение с `googlevideo.com`) напрямую дважды за `YT_RETRY_WIN` принял
ClientHello и замолчал, его стойка (/28 — YOTA режет стойками) на 12 ч попадает в список сети
(`/data/adb/vpn_tether_ytramp`, не больше 128 на сеть: 32 на YOTA набирались за час). Если стойка из
списка молчит и с малым окном, запись не продлевается, а в журнале — «молчит и с малым окном». Её соединения nfqws2 ведёт первым профилем: окно приёма — 2 байта с
ClientHello до первых байт ответа, дальше обычное, но не больше 128 КБ (функция `vt_wssize_ramp` в
`zapret2/lua/vpn-tether.lua`; все исходящие пакеты к этим адресам идут в очередь, цепочка
`VPN_YT_RAMP`). Готовый `wssize` тут не годится: он снимает подмену на ClientHello, а масштаб окна
в SYN уже занижен — ядро шлёт окно под свой масштаб, и сервер видит его в сотни раз меньше
(на YOTA TLS 1,9 с и почти нулевая скорость). Стенд 15.11 (YOTA, 17 молчащих стоек × 2 круга):
34 из 34 против 19–28 без него; TLS 0,84 с против 0,37 (сервер держит первые байты до своего
таймера); скорость — до ~5 Мбит/с на соединение при RTT 150 мс. В статусе — «малое окно: N групп
адресов». Настоящий масштаб окна соединения хранит nfqws2: с малым окном он помнит соединение без
пакетов час, а не 5 минут (`--ctrack-timeouts`), а при его перезапуске модуль рвёт соединения
к стойкам из списка: телефона — сразу, клиентам раздачи — RST на их следующий пакет (приложение откроет
новые).

## DNS

- **Напрямую:** DNS клиентов раздачи (любой :53) перенаправляется на локальный dnsproxy
  (порт 5354, закрыт для всех, кроме раздачи и lo). Оператор видит только TLS до DoH-сервера.
- **VPN:** по умолчанию DNAT в DNS VPN-клиента. Режимы `cache`/`doh` включаются, только если
  трафик root реально идёт в туннель.
- **Проверка здоровья:** запрос со случайным именем, чтобы кэш не маскировал сбой.
  Медленнее 3000 мс считается отказом. Проверки идут только при реальном использовании DNS,
  поэтому модем может спать. Если основной DoH молчит, dnsproxy переходит на запасные.
  Вернуться на основной можно не раньше чем через 10 мин и после 2 удачных проверок подряд;
  если основной «дёргается» (2 ухода за 30 мин), запасные держатся 30 мин. Если молчат все,
  DNS временно идёт обычным путём (оператор или VPN) с перепроверкой раз в `DNS_HEALTH_RECOVER`.
- **Кэш dnsproxy** (с 3.17) сбрасывается при каждом возврате на DoH: и с запасных на основной,
  и с обычного DNS на dnsproxy. Вручную — кнопка «Сбросить кэш DNS» (Сервис → Проверки),
  если сайт пишет «недоступно в вашем регионе». Кэш самого ноутбука модуль не трогает: после
  сброса на нём нужен `ipconfig /flushdns` или переподключение к точке.
- dnsproxy перезапускается при смене маршрута (VPN ↔ WAN, Wi-Fi ↔ мобильная), чтобы старое
  keep-alive DoH-соединение не зависало. Если dnsproxy не запустился, раздача получает обычный
  DNAT, а модуль пытается вернуть dnsproxy раз в ~минуту.
- CA-сертификаты для dnsproxy берутся из системного хранилища (APEX conscrypt на Android 14+).

## Защита от утечек

- **Kill-switch** (`KILL_SWITCH`, fail-closed). Если правила VPN не встали или их снёс
  netd/Tethering, трафик клиентов отбрасывается, а не уходит напрямую с реальным IP. Сторож
  правил раз в ~6 с проверяет `ip rule` и хуки цепочек и пересобирает их.
  С `KILL_SWITCH_STRICT=1` раздача стоит на паузе, пока в режиме VPN сам VPN не поднят.
  Без него (по умолчанию) после 3 промахов раздача уходит напрямую.
- **Утечки мимо netfilter.** Модуль выключает аппаратный tethering offload и снимает
  tc-фильтры BPF offload (Android 13+), через которые старые соединения клиента шли мимо VPN.
  При смене режима делается адресный сброс conntrack (только подсети раздачи, через `bin/conntrack`).
- **Скрытие раздачи от оператора** (`TETHER_STEALTH`): `net.tethering.noprovisioning`
  (ставит `post-fs-data.sh` на раннем этапе загрузки), TTL телефона 63, учёт (и по желанию
  отбой, `TETHER_TTL_STRICT`) пакетов раздачи с «чужим» TTL.
- **QUIC:** закрыть HTTP/3 выбранным приложениям телефона (`QUIC_BLOCK_APPS`) и раздаче
  (`ZAPRET_QUIC_BLOCK`), чтобы они сразу шли по TCP, где работает обход.
- **Состояние в описании модуля** в списке модулей KernelSU/Magisk (`STATUS_IN_DESCRIPTION`).

## Структура репозитория

- `module/` — сам модуль:
  - `service.sh` — демон: журнал изменений, блок настроек `USER CONFIG`, чтение
    `vpn_tether.conf`, служебные вызовы для WebUI, переменные, запуск; функции — в `lib/`:
    - `lib/common.sh` — журнал, статус и описание модуля;
    - `lib/net.sh` — интерфейсы, tun/VPN, WAN, поиск раздачи, профили сети и sysctl;
    - `lib/dns.sh` — DNS клиентов, dnsproxy, проверки DoH, Meta, DNS телефона;
    - `lib/zapret.sh` — обход DPI (nfqws), QUIC приложений;
    - `lib/youtube.sh` — кэши оператора, повтор застрявших видеосоединений;
    - `lib/stealth.sh` — скрытие раздачи (TTL);
    - `lib/rules.sh` — правила раздачи, kill-switch, conntrack, HW offload;
    - `lib/loop.sh` — главный цикл, перечитывание настроек, выход;
  - `action.sh` — кнопка Action;
  - `webctl.sh` + `webroot/index.html` — WebUI;
  - `customize.sh` — установка (выбор бинарников, создание конфига);
  - `post-fs-data.sh` — ранний этап загрузки (`noprovisioning`);
  - `zapret/` — `scan.sh` (подбор, сторож, сайты), `netid.sh`, списки доменов,
    сети Google, файлы подделок ClientHello/QUIC;
  - `bin/` — `nfqws`, `dnsproxy`, `conntrack` под arm64/armv7.
- `third_party/conntrack/` — исходники статического `conntrack` (GPL), в модуль не входят.
- `tools/` — вспомогательные скрипты разработки (сканер блокировок, замеры, отладка);
  в модуль не входят.
